# Paddle: фактические начисления, версия 2

## Границы изменения

Новая схема охватывает разовые продажи маркетплейса, подписки авторов (Premiere Gal, Spunkram и продукты с `subs_system=1`), их продления и Lifetime. Для отдельных пакетов AI-кредитов сохраняется существующая выдача кредитов; финансовый журнал учитывает доход платформы без придумывания доли автора.

**Creator / Creator AI самого MotionFlow исключены**, включая их аффилиатные комиссии, доплаты и возвраты. Исключение определяется Price ID / типом продукта и существующей атрибуцией подписки, а не тем, какой сервер получил webhook. Смешанный заказ с Creator и авторским продуктом не рассчитывается приблизительно: он остаётся ожидающим проверки.

Граница — `paddle_accounting_settings.enabled_from`, UTC с микросекундами, выставляется только при первом `enable`. Решение принимается по `transaction.created_at`, а не по дате доставки webhook. Старая транзакция не становится новой при повторной доставке или позднем возврате. Новое продление старой подписки имеет новый transaction ID и после границы использует v2.

Миграция только добавляет таблицы. Она не пересчитывает, не переносит и не исправляет старые начисления. До отдельного включения поведение сайта прежнее.

## Данные и расчёт

- Единственный финансовый writer: `lib/paddle-accounting/engine.mjs`. Laravel передаёт подходящие события подписанным запросом во внутренний endpoint Next.js. Оригинальная подпись Paddle проверяется в обоих входных обработчиках.
- Источник комиссии и чистой выручки: `details.payout_totals.fee` / `earnings` после `completed`. Нулевая комиссия допустима. При `null`, незавершённом платеже или неполных данных — pending, без изменения баланса и без fallback `5% + $0.50`.
- Сохраняются исходный и окончательный payload, исходная валюта, валюта выплаты, transaction / line IDs, суммы комиссии/выручки, снимок условий и каждое движение получателя. Основные суммы — целые минимальные единицы валюты; внутренние произведения и деления используют BigInt.
- Существующие денежные балансы сайта — USD. Оплата в другой валюте поддерживается через фактический USD payout Paddle. Выплата Paddle не в USD остаётся pending, чтобы не смешивать валюты одного баланса.
- Комиссия всего заказа распределяется пропорционально суммам позиций после скидки с налогом. Выручка до комиссии распределяется по базе без налога после скидки. Остатки центов — largest remainder с постоянным порядком по line ID. Суммы всех строк точно сходятся с Paddle. Используются `line.totals`, включая quantity, а не `unit_totals`.
- Для маркетплейса сохраняются ставки Personal / Extended, `extra_tax`, соавторы и ставки реферала. Реферальная выплата учитывается отдельно как затрата платформы. Для авторских подписок сохраняется доля автора 45% чистой выручки (`90% / 2`); округление half-up, остаток принадлежит платформе.
- Legacy-таблицы служат совместимыми проекциями для доступа и текущих кабинетов. В журнале остаются исходный платёж и отдельные корректировки. Старые целочисленные поля `price` / `sold_summary` не используются как источник расчёта v2.

Идемпотентность: `(account, environment, transaction_id)`, `(transaction_row_id, line_id)`, `(account, environment, adjustment_id)` и уникальный ключ каждого движения. Изменение баланса, проекций и движений выполняется одной SQL-транзакцией. Advisory lock сериализует обработку платежа. При ошибке нет частичного начисления; запись остаётся pending для повторной обработки. Версия платежа сохраняется даже после `disable`.

## Возвраты и отмены

Обрабатываются `adjustment.created` и `adjustment.updated`. Только одобренный `action=refund` меняет деньги. Pending approval / rejected не списывают доход. Используются фактические `payout_totals.earnings` и `retained_fee`, а также связанные item IDs; частичный возврат не обнуляет весь заказ. Несколько возвратов пересчитывают оставшуюся долю по сохранённым условиям, а не по текущим процентам автора.

Возврат только налога может увеличить earnings; положительная корректировка начисляется правильно. Удержанные Paddle fees относятся на платформу, как в прежней политике маркетплейса. Возврат старого периода использует его запись журнала и не прекращает более новое продление.

Отмена / past_due для подписки, уже принадлежащей v2, меняет состояние доступа, но не списывает заработок. Деньги изменяются отдельной одобренной финансовой корректировкой. Историческая ветка и собственные подписки сайта сохраняют прежнее поведение.

Неразрешённая атрибуция продукта, корзина с несколькими подписными продуктами и действия `chargeback*` / `credit*` остаются pending для проверки. Они не трактуются как полный refund. В этой версии автоматическое финансовое применение реализовано для полных, частичных и налоговых refund.

Sandbox не меняет реальные балансы и проекции общей БД: новые записи остаются pending. Sandbox/production и два Paddle-аккаунта имеют разные ключи журнала.

## Проверки

```powershell
node --test scripts/test-paddle-accounting.mjs
$env:PADDLE_ACCOUNTING_TEST_MYSQL='1'
node --test --test-concurrency=1 scripts/test-paddle-accounting.mjs
npx tsc --noEmit --incremental false
```

Интеграционные тесты создают **TEMPORARY** таблицы на отдельном MySQL-соединении, в том числе для `users`, продаж и подписок. Они затеняют все имена, которые изменяет engine, и исчезают при закрытии соединения. Рабочие таблицы не изменяются. Нужна привилегия CREATE TEMPORARY TABLES. Не запускайте production webhook с тестовым payload вместо этих тестов.

Нативный PHP CLI локально отсутствует: PHP-файлы проверены PHP 8.3 parser; перед активацией обязательны штатная Laravel CI-проверка и smoke-test внутреннего моста на сервере.

Проверка этой реализации: 26 тестов прошли, включая реальные MySQL-транзакции во временных таблицах, оба кабинета, подписи внутреннего моста и защиту подписок сайта. TypeScript и production-сборка Next.js прошли. Новая функция расчёта также сверена GET-запросами с четырьмя production-платежами: НДС, скидка, продление и Lifetime; комиссия и net сошлись с Paddle. Production-схема, настройки Paddle и рабочие начисления при разработке не менялись.

## Включение на сервере

1. Сохранить исходники обоих приложений, `.env` и обычный snapshot БД. Развернуть оба приложения с выключенной новой схемой. Не включать старый отключённый Laravel webhook только ради этого изменения.
2. Добавить в оба окружения один `PADDLE_ACCOUNTING_BRIDGE_SECRET` минимум 32 случайных символа. В Laravel установить `PADDLE_ACCOUNTING_DEFAULT_WEBHOOK_SECRET` и, если используется, `PADDLE_ACCOUNTING_SPUNKRAM_WEBHOOK_SECRET` для его собственных Paddle destinations; секреты разных destinations могут отличаться. Эти отдельные настройки не заменяют секрет старого обработчика. `PADDLE_ACCOUNTING_BRIDGE_URL` по умолчанию `http://127.0.0.1:3000/api/internal/paddle-accounting`.
3. Применить только новую Laravel-миграцию штатным процессом либо из каталога Next.js выполнить `node scripts/paddle-accounting.mjs schema`. SQL в обоих проектах идентичен и идемпотентен; активация отдельно. Не переисполнять старые миграции с backfill подписок.
4. Проверить исходные HTTP-подписи, доступ Laravel → Next.js, публикацию записей в обоих кабинетах и отсутствие изменений в Creator / Creator AI. Активная production destination сейчас ведёт в Next.js. В её подписки рекомендуется добавить `adjustment.created`; reconciliation worker также восстанавливает пропущенные события.
5. Запустить worker из **текущего release-каталога Next.js**:

   ```sh
   pm2 start deploy/paddle-accounting-worker.config.cjs
   pm2 save
   node scripts/paddle-accounting.mjs status
   ```

6. После первой успешной итерации выполнить `node scripts/paddle-accounting.mjs enable`. Команда проверяет четыре Price ID исключённых Creator / Creator AI, InnoDB всех финансовых таблиц, свежесть worker heartbeat и один раз фиксирует текущую дату UTC. Это согласованный момент перехода. Нельзя ставить дату задним числом.
7. Проверить первый новый платёж и возврат; `status` показывает pending/applied. Worker раз в минуту последовательно повторяет pending и сверяет новые после границы платежи/корректировки через GET Paddle. Денежных запросов в Paddle он не делает. Перед следующим deploy обновить PM2 worker на новый release через `pm2 delete motionflow-accounting` и `pm2 start deploy/paddle-accounting-worker.config.cjs`; не оставлять его на очищаемом старом release.

## Быстрый откат

**До активации** можно восстановить исходные файлы из бэкапа и удалить добавленные файлы по манифесту. Схема журнала может остаться; без включения она не участвует в начислениях.

**После активации** сначала выполнить:

```sh
node scripts/paddle-accounting.mjs disable
```

Новые транзакции больше не переходят на v2. Уже принадлежащие v2 платежи, их повторные события и возвраты продолжают идти через журнал; worker оставляется работающим. Поэтому после первых начислений нельзя просто подменить webhook старым файлом: он не знает о новых idempotency-ключах. Не удалять журнал и не восстанавливать старый snapshot балансов поверх новых движений.

Локальный исходный бэкап этой задачи: `D:\Packs\MotionFlow.pro\_Site-backups\paddle-actual-2026-10-21T13-21-44-235Z`. Он содержит исходные файлы, SHA-256 и исходные HEAD обоих репозиториев; `restore.mjs` блокирует восстановление после появления новых journal rows и при чужих правках файлов.

## Защищённые серверные операции

Workflow `release.yml` принимает `accounting_operation`: `inspect`, `backup`, `prepare`, `verify`, `enable`, `status`, `disable`. При выборе операции сборка и деплой пропускаются. Используются уже настроенные SSH secrets; значения ключей и `.env` не выводятся. Для `prepare` / `verify` / `enable` передаются полные `accounting_next_commit` и `accounting_laravel_commit`: фактически запущенные релизы должны точно совпасть.

`backup` сохраняет полные архивы двух релизов, отдельные исходные `.env`, PM2 и consistent dump всей базы в `/root/motionflow-accounting-backups/<UTC>`, проверяет архивы и SHA-256. `prepare` сверяет этот бэкап, получает секреты именно Laravel destinations через GET Paddle, создаёт общий ключ моста и запускает worker при выключенных начислениях. `verify` проверяет оба health endpoint, нативный PHP/Blade, исходные подписи, мост и все 26 тестов на временных MySQL-таблицах; проверяет неизменность прежних финансовых записей и балансов. `enable` требует успешный preflight за последние 30 минут, бэкап и свежий heartbeat, затем фиксирует текущее время БД.

После первых v2 платежей для быстрого безопасного отключения новых начислений используется `accounting_operation=disable`. Уже созданный журнал и обработчик его возвратов нужно сохранить. Полные архивы и dump предназначены для аварийного восстановления под контролем, а не для перезаписи актуальных балансов после новых платежей.
