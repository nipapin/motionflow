# Очереди запросов Replicate

Все серверные генерации, использующие `trackedReplicateFetch`, проходят через
`lib/replicate-request-queue.ts`. Выбор API-ключа остаётся в `getReplicateApiToken`:
Motion Flow, Spunkram Library, Gal Toolkit MAX и Odin Pro используют свои очереди.
Очередь относится к ключу автора, а не к пользователю, который запускает генерацию.
Если один ключ случайно указан у нескольких авторов, они разделяют очередь.

Redis хранит порядок ожидания, активные слоты и паузу после 429. Все процессы
и экземпляры сайта должны подключаться к одному Redis через существующие
`REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`, `REDIS_DB`. Новые зависимости,
миграции БД и отдельный worker не нужны. После развёртывания кода очередь
включается автоматически. При недоступности Redis запрос получает 503;
отправка в обход очереди запрещена.

На каждом ключе две независимые FIFO-очереди: создание predictions и остальные
API-вызовы, включая опрос результата и отмену. Поэтому длинный запрос запуска
не занимает слот опроса статуса. Загрузки с CDN/replicate.delivery обходят эти
очереди. Успешные ответы продолжают записываться в статистику AI Usage.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `REPLICATE_QUEUE_CREATE_CONCURRENCY` | 8 | Одновременные HTTP-запросы создания |
| `REPLICATE_QUEUE_CREATE_INTERVAL_MS` | 250 | Минимальный интервал между отправками создания |
| `REPLICATE_QUEUE_OTHER_CONCURRENCY` | 16 | Одновременные остальные HTTP-запросы |
| `REPLICATE_QUEUE_OTHER_INTERVAL_MS` | 50 | Минимальный интервал между остальными отправками |
| `REPLICATE_QUEUE_MAX_PENDING` | 200 | Максимум ожидающих в каждой очереди |
| `REPLICATE_QUEUE_WAIT_TIMEOUT_MS` | 180000 | Максимальное ожидание слота |
| `REPLICATE_QUEUE_REQUEST_TIMEOUT_MS` | 90000 | Таймаут одного отправленного HTTP-запроса |

Любую настройку можно переопределить для автора, вставив `DEFAULT`, `SPUNKRAM`,
`TOOLKIT` или `ODINPRO` после `REPLICATE_QUEUE_`, например:

```dotenv
REPLICATE_QUEUE_SPUNKRAM_CREATE_INTERVAL_MS=1000
REPLICATE_QUEUE_TOOLKIT_CREATE_CONCURRENCY=4
```

При повторном использовании одного ключа у нескольких авторов задавайте им
одинаковые настройки. Интервалы ограничивают частоту отправки; concurrency
ограничивает HTTP-соединения, а не число выполняющихся на Replicate моделей.
Текущий SDK может держать запрос создания открытым до получения результата,
поэтому очередь при всплеске длинных генераций может ждать заметно дольше,
чем следует только из интервала отправки.

По документации [Replicate](https://replicate.com/docs/topics/predictions/rate-limits),
обычные лимиты — 600 запусков в минуту и 3000 остальных запросов в минуту.
Дефолтные интервалы ниже этих пределов. При низком балансе действуют более
строгие ограничения; очередь не может гарантировать отсутствие 429.

Ответ 429 устанавливает общую для ключа паузу: сначала используется
`Retry-After` (секунды или HTTP-дата), затем время из `detail`, иначе 60 секунд.
Пауза одного ключа не блокирует другие ключи. Повторами занимается существующий
Replicate SDK: каждая попытка снова проходит очередь и ждёт окончания паузы.
Дополнительных автоматических повторов платного POST при сетевой ошибке или
5xx этот слой не добавляет. Локальное переполнение/таймаут возвращает 503,
чтобы SDK не воспринимал его как provider 429 и не повторял POST.

При отмене переданного AbortSignal ожидающий запрос удаляется без отправки.
После завершения или ошибки слот освобождается; после аварийного завершения
процесса ожидающие записи и активные слоты истекают автоматически. В Redis
попадают только SHA-256 отпечаток ключа, случайные ID и служебные числа;
API-ключи, промпты и результаты туда не записываются.

Это очередь исходящих запросов внутри текущего HTTP-запроса к сайту, а не
долговечная очередь фоновых заданий. Ожидающие генерации не возобновляются
после перезапуска приложения. При переполнении или превышении времени
ожидания клиент получает временную ошибку через существующий API генераций.
Таймауты reverse proxy и клиента должны учитывать дополнительное ожидание.
